# 成本與可觀測性

| 架構決定 | 成本來源 | 觀測與改善 |
|---|---|---|
| EC2/ASG | instance 時數、規格、購買模式 | CloudWatch CPU/自訂指標、right sizing、適當自動擴縮 |
| EBS/EFS/S3 | 容量、IOPS/吞吐、請求、取回與 lifecycle | volume metrics、存取型態、舊版本與 snapshot 清理 |
| NAT gateway | 時數及處理資料量，並可能有跨 AZ/對外傳輸費 | 比對 S3 gateway endpoint 或其他合適 endpoint 的成本與路徑 |
| ALB/CloudFront | 使用時間、容量/請求、資料傳輸 | cache hit ratio、origin load、流量模式 |
| RDS/Aurora/DynamoDB | instances/儲存/I/O 或 capacity/請求 | Performance Insights/CloudWatch、capacity 模式選擇 |

EC2 On-Demand 適合彈性需求；Savings Plans/Reserved Instances 適合穩定用量與承諾；Spot 適合可中斷、可重試負載，不把它當唯一關鍵 HA 容量。具體折扣及條件依官方定價更新。運算之外也看資料傳輸、NAT、備份與閒置資源。

**CloudWatch** 觀測 metrics、logs、alarms；**CloudTrail** 記錄 AWS API 活動；**AWS Budgets/Cost Explorer** 支援預算與花費分析。看到 `AccessDenied` 先分辨權限與路由，見 [[EC2與IAM安全]]、[[EC2與網路]]。費用通常是架構設計結果，做 Lab 前設定預算提示，結束後清除資源。

# 深化

## 資料傳輸費：帳單上最常被忽略的一塊

Domain 4 有一整類題目在問「如何降低資料傳輸成本」，而規則其實很固定：

| 流向 | 費用 |
|---|---|
| **進入 AWS（inbound）** | **免費** |
| **同一 AZ 內、使用私有 IP** | **免費** |
| **跨 AZ（同 Region）** | **雙向計費** |
| **跨 Region** | 計費（較貴） |
| **出到網際網路（egress）** | **最貴** |
| **經 CloudFront 出去** | **比直接從 origin 出去便宜**，且 CloudFront 到 origin 的回源免費 |
| **S3 / DynamoDB 經 gateway endpoint** | **免費**（相對走 NAT gateway 要付處理費） |

> [!danger] 三個標準降本手法
> **(1) 私有子網要存取 S3/DynamoDB → 用 gateway endpoint 取代 NAT gateway。** 免費 vs 按 GB 計費，這是最經典的成本題。
> **(2) 大量對外流量 → 放 CloudFront 前面。** 同時降低 egress 單價與 origin 負載。
> **(3) 跨 AZ 流量能省則省。** 例如讓每個 AZ 的私有子網指向**自己 AZ 的 NAT gateway**，而不是全部指向單一 AZ 的 NAT。

## CloudWatch 深入

| 功能 | 重點 |
|---|---|
| **預設指標** | EC2 預設提供 CPU、網路、磁碟 I/O，**間隔 5 分鐘**；啟用 **detailed monitoring** 變 1 分鐘（付費） |
| **CloudWatch Agent** | **記憶體使用率與磁碟可用空間不是預設指標**，必須安裝 agent 才收得到。這是高頻考點 |
| **自訂指標** | `PutMetricData`；**high-resolution** 可到 1 秒 |
| **Logs** | 日誌集中；**保留期預設永久**，應設定保留期以控制成本 |
| **Logs Insights** | 對日誌下查詢語法做分析 |
| **訂閱過濾器（Subscription filter）** | 即時把日誌串到 **Lambda / Firehose / Kinesis**，用於集中式日誌平台 |
| **Alarm** | 可觸發 SNS、Auto Scaling、EC2 動作；**composite alarm** 組合多條件降低告警噪音 |
| **Metric filter** | 從日誌文字萃取出指標（例如統計 `ERROR` 出現次數）後再告警 |
| **Contributor Insights / ServiceLens / Synthetics** | 貢獻者分析、端到端追蹤、主動式監控 |

> [!important] 兩個必記結論
> **(1) 「要監控 EC2 的記憶體使用率」→ 安裝 CloudWatch Agent。** 選項若說「直接在 CloudWatch 看記憶體指標」是錯的。
> **(2) 「要從應用日誌中偵測特定錯誤並告警」→ metric filter + alarm**（不是直接對 log 設 alarm）。

## 三個觀測服務的分工（再次強調，因為真的很常錯）

| 問題 | 服務 |
|---|---|
| 系統跑得怎麼樣？（CPU、延遲、錯誤率） | **CloudWatch** |
| 誰呼叫了哪個 API？ | **CloudTrail** |
| 資源設定是什麼？有無違規？ | **AWS Config** |
| 微服務之間哪一段慢？ | **X-Ray**（分散式追蹤） |

## 成本管理工具

| 工具 | 用途 | 題幹關鍵字 |
|---|---|---|
| **Cost Explorer** | 視覺化分析歷史花費、預測、RI/SP 建議 | `analyze spending trends`、`forecast` |
| **AWS Budgets** | 設定預算門檻並**告警**（成本、用量、RI 覆蓋率） | `alert when spending exceeds`、`notify before exceeding budget` |
| **Cost and Usage Report (CUR)** | 最細粒度的帳單明細，可送 S3 給 Athena/QuickSight 分析 | `detailed line items`、`custom analysis` |
| **Cost Allocation Tags** | 依標籤歸因成本到團隊/專案 | `chargeback`、`show costs per department` |
| **Cost Anomaly Detection** | 機器學習偵測異常花費 | `detect unexpected spend` |
| **Compute Optimizer** | 依實際使用率給規格建議 | `right-size`、`recommendations based on utilization` |
| **Trusted Advisor** | 含閒置資源與低使用率檢查（完整檢查需 Business/Enterprise Support） | `idle resources`、`underutilized` |
| **Organizations 合併帳務** | 級距折扣、**RI/Savings Plans 跨帳號共享** | `multiple accounts`、`volume discounts` |

> [!tip] Budgets vs Cost Explorer
> **要「告警」→ Budgets。要「分析」→ Cost Explorer。** 題目問「超過預算時通知團隊」一定是 **Budgets**。

## 成本最佳化的五個提問

遇到 Domain 4 的題目，照這個順序想：

1. **有沒有完全不需要的資源？** 閒置 EC2、未掛載的 EBS、未關聯的 EIP、舊 snapshot、未完成的 multipart upload。
2. **規格對嗎？** Compute Optimizer 的 right-sizing。
3. **購買模式對嗎？** 穩定用量 → Savings Plans；可中斷 → Spot。見 [[運算與容器選型]]。
4. **儲存類別對嗎？** Lifecycle 轉冷、Intelligent-Tiering。見 [[S3與資料生命週期]]。
5. **資料傳輸路徑對嗎？** gateway endpoint、CloudFront、跨 AZ 流量。

> [!warning] 「最省」不等於「最便宜的那個選項」
> 題幹的其他限制（可用性、延遲、合規、不可中斷）會先淘汰掉一批選項。
> **先用硬性條件篩選，剩下的才比價**——這個順序反過來就會落入陷阱。原筆記在 [[模考與錯題模板]] 已提醒，這裡給出具體操作順序。
