# 🧠 技術層
*它實際上怎麼運作——心智模型、機制、限制。**第一輪只讀這一層**，先把架構直覺建立起來。*

## 以一個電商訂單系統為例

用 **C4 Model** 的兩個層級來看同一套系統：**L1 先定邊界**（誰用它、它跟誰往來），**L2 再拆內部**（有哪些容器、資料怎麼流）。AWS 服務只在 L2 出現——L1 刻意不談技術。

### L1：System Context（系統情境）

```mermaid
flowchart TB
    U["消費者<br/>[Person]<br/>瀏覽商品、下訂單、查詢物流"]
    OPS["營運人員<br/>[Person]<br/>維護商品、處理退貨"]

    SYS["電商訂單系統<br/>[Software System]<br/>商品瀏覽、下單、金流、出貨通知"]

    PAY["第三方金流<br/>[External System]<br/>刷卡授權與請退款"]
    MAIL["郵件 / 簡訊供應商<br/>[External System]"]
    ERP["地端 ERP<br/>[External System]<br/>庫存與財務主檔"]

    U -->|"HTTPS 瀏覽與下單"| SYS
    OPS -->|"HTTPS 後台操作"| SYS
    SYS -->|"請款 / 退款 API"| PAY
    SYS -->|"訂單與出貨通知"| MAIL
    SYS <-->|"庫存同步<br/>走 VPN 或 Direct Connect"| ERP

    classDef person fill:#08427b,stroke:#052e56,color:#fff
    classDef system fill:#1168bd,stroke:#0b4884,color:#fff
    classDef ext fill:#999999,stroke:#6b6b6b,color:#fff
    class U,OPS person

```

> [!tip] L1 的用途
> 它回答「**系統的邊界在哪**」。考題裡的 `data residency`、`must not traverse the public internet`、`partners upload via SFTP`，談的都是**跨越這條邊界**的流量——先畫 L1，就知道該在哪一段套 Direct Connect、PrivateLink 或 Transfer Family。

### L2：Container（容器視圖）

把 L1 那個方塊拆開，這一層才出現 AWS 服務：

```mermaid
flowchart TB
    U["消費者<br/>[Person]"]
    OPS["營運人員<br/>[Person]"]

    subgraph SYS["電商訂單系統 — 單一 AWS Region"]
        direction TB
        DNS["Route 53<br/>[Container: DNS]<br/>Alias 記錄、health check、failover"]
        EDGE["CloudFront + WAF<br/>[Container: CDN 與 L7 防護]<br/>快取靜態資產、擋 SQLi/XSS"]
        ALB["ALB<br/>[Container: L7 負載平衡]<br/>public subnet、跨 2 AZ"]

        subgraph PRIV["private subnets（跨 2 AZ）"]
            direction LR
            APP["訂單服務<br/>[Container: ECS / EC2 ASG]<br/>Spring Boot，無狀態"]
            WORKER["出貨 worker<br/>[Container: ECS / Lambda]<br/>非同步處理"]
        end

        DB[("RDS / Aurora Multi-AZ<br/>[Container: 關聯式資料庫]<br/>訂單、庫存、交易")]
        CACHE[("ElastiCache Redis<br/>[Container: 快取與 session]")]
        OBJ[("S3<br/>[Container: 物件儲存]<br/>商品圖、發票 PDF")]
        MSG["SNS + SQS<br/>[Container: 非同步訊息]<br/>解耦與緩衝"]
    end

    PAY["第三方金流<br/>[External System]"]
    ERP["地端 ERP<br/>[External System]"]

    U --> DNS
    OPS --> DNS
    DNS --> EDGE
    EDGE --> ALB
    EDGE -.->|"靜態資產<br/>OAC 保持 bucket 私有"| OBJ
    ALB --> APP
    APP --> DB
    APP --> CACHE
    APP --> OBJ
    APP -->|"發布訂單事件"| MSG
    MSG --> WORKER
    WORKER --> DB
    WORKER -->|"請款"| PAY
    WORKER <-->|"庫存同步"| ERP

    classDef person fill:#08427b,stroke:#052e56,color:#fff
    classDef container fill:#438dd5,stroke:#2e6295,color:#fff
    classDef store fill:#438dd5,stroke:#2e6295,color:#fff
    classDef ext fill:#999999,stroke:#6b6b6b,color:#fff
    class U,OPS person
    class DNS,EDGE,ALB,APP,WORKER,MSG container
    class DB,CACHE,OBJ store
    class PAY,ERP ext
```

> [!important] L2 圖上藏著四個高頻考點
> **① 為什麼 ALB 在 public subnet、應用在 private subnet**——應用不需要 public IP。
> **② 為什麼要有 SNS + SQS 這一層**——出貨慢不能拖垮下單；下游各自緩衝與重試。
> **③ 為什麼 CloudFront 有一條虛線直接連到 S3**——靜態資產走 OAC，bucket 全程保持私有。
> **④ 這張圖上完全沒有 NAT gateway**——因為 APP 對 S3 走的是 gateway endpoint（免費）。真要出公網才需要 NAT，而且要**每 AZ 一個**。

> [!note] 為什麼用 flowchart 而不是 mermaid 的 C4 語法
> mermaid 的 `C4Context` / `C4Container` 目前仍是 experimental，在 GitHub 與部分編輯器上不保證能渲染。
> 這裡用 `flowchart` + `subgraph` + `classDef` 畫出等價的 C4 語意（Person / Container / External System 以顏色區分，型別寫在標籤中），**在任何地方都能正常顯示**。

這只是候選架構：CloudFront 可以加速適合快取的內容；若動態請求不適合快取，仍可經 ALB 到應用。儲存、DB、佇列各自服務不同資料需求。

## 從需求回推

`高可用 HTTP API` → ALB + target group + 多 AZ ASG；狀態放在外部持久服務。`private subnet 訪問 S3` → S3 gateway endpoint + IAM/bucket policy（依限制）；`共享 Linux 檔案` → EFS mount target/NFS；`延遲解耦` → SQS；`global static files` → S3 + CloudFront + OAC。這些是常見解法，仍需逐題檢查可用性、資料一致性及成本條件。

1. 不看筆記，畫出一個高可用電商訂單系統：從使用者到資料庫，標出每一層的服務與故障邊界。
2. 「使用者到應用」這條路徑上，誰終止 TLS？憑證放哪？健康檢查由誰做？
3. 「應用到 AWS API」這條路徑，網路可達與有授權各需要滿足什麼？
4. 同一張圖上，依序假設「單台實例死亡 → 整個 AZ 失效 → 整個 Region 失效」，每層需要什麼機制？
5. 在這張圖上標出五個計費點，並說出哪一個最容易被低估。

<details>
<summary>參考答案</summary>

1. 骨架：`Route 53 → CloudFront（可選）→ WAF → ALB（public subnet，跨 2 AZ）→ ASG EC2/ECS（private subnet，跨 2 AZ）→ RDS Multi-AZ（private subnet）`，旁支 `→ SQS/EventBridge → worker`、`→ S3`、`→ ElastiCache`。故障邊界：實例（ASG 替換）、AZ（多 AZ 部署）、Region（跨 Region 複寫 + DNS/GA 切換）。
2. **TLS 通常在 CloudFront 或 ALB 終止**。憑證用 **ACM**——CloudFront 的必須在 **us-east-1**，ALB 的用同 Region。健康檢查由 **target group** 對後端做，**ASG 要把 health check type 設為 ELB** 才會依此替換實例。
3. **網路可達**：route table（gateway/interface endpoint 或 NAT）、SG 出站、NACL 雙向。**有授權**：IAM identity policy、資源 policy、endpoint policy、SCP、KMS。**兩者是獨立的兩道檢查**——網路通不代表有權限（症狀：403 而非 timeout）。
4. **實例** → ALB health check + ASG 替換（狀態須外部化）；**AZ** → 多 AZ ASG/ALB/RDS Multi-AZ，**NAT 與 subnet 也要每 AZ 規劃**；**Region** → 跨 Region 資料複寫 + Route 53 或 Global Accelerator 切換 + 環境預先部署 + 演練。
5. 計費點：EC2 時數、ALB 容量與流量、NAT gateway 時數與處理量、RDS instance 與儲存、跨 AZ 傳輸、對外 egress。**最容易被低估的是 NAT gateway 的資料處理費與跨 AZ 流量費**——尤其當流量其實是去 S3（可改用免費的 gateway endpoint）。

</details>
