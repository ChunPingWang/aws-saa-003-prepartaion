# 第一輪｜Q1–Q30

## Domain 1｜設計安全架構（30%）

## Q1
一家公司的行動 App 預計有 200 萬名使用者，需要讓使用者以 Google 或 Apple 帳號登入，登入後**直接從手機上傳照片到 S3**。應徵的解決方案要維運負擔最低。

- A. 為每位使用者建立一個 IAM user，發放 access key
- B. 使用 Cognito User Pool 處理登入，搭配 Cognito Identity Pool 換取 AWS 臨時憑證
- C. 在 EC2 上自建認證服務，將 IAM role 的長期憑證嵌入 App
- D. 使用 IAM Identity Center 管理這些使用者

> [!success]- 解答：**B**
> **為什麼對**：終端使用者的認證用 **User Pool**（支援社群登入），而「手機**直接**存取 S3」需要 AWS 臨時憑證，這只有 **Identity Pool** 能提供。
> **為什麼其他錯**：
> **A** — IAM user 不是為終端使用者設計，有帳號層級數量上限，且發放長期 access key 是反模式。
> **C** — 把任何長期憑證嵌入客戶端一律排除。
> **D** — IAM Identity Center 是給**員工**存取 AWS 帳號用的，不是 App 終端使用者。
> **關聯**：[[身分聯合與應用存取]]

## Q2
稽核團隊要求：必須能查出**過去某位管理員在什麼時間刪除了哪個 S3 bucket**，且稽核日誌本身不可被竄改。

- A. 啟用 CloudWatch Logs 並設定保留期
- B. 啟用 AWS Config 記錄組態變更
- C. 啟用 CloudTrail、送到專用帳號的 S3、開啟 log file validation 與 Object Lock
- D. 啟用 VPC Flow Logs

> [!success]- 解答：**C**
> **為什麼對**：「誰在何時呼叫了哪個 API」是 **CloudTrail** 的定義。不可竄改靠 **log file validation**（雜湊驗證）+ **S3 Object Lock**（WORM）+ 跨帳號隔離。
> **為什麼其他錯**：
> **A** — CloudWatch 記錄「表現」不是「動作」。
> **B** — Config 記錄「資源設定狀態」，能告訴你 bucket 設定變了，但**誰做的**要問 CloudTrail。這組是最常見的干擾配對。
> **D** — Flow Logs 是網路連線中繼資料。
> **關聯**：[[治理與合規]]

## Q3
EC2 位於私有子網，需要讀取 S3 上以 **SSE-KMS** 加密的物件。已建立 S3 gateway endpoint、instance profile 也附了 `s3:GetObject`，但仍收到 `AccessDenied`。

- A. 把 EC2 移到公有子網並指派 public IP
- B. 在 KMS key policy 或 IAM policy 中授予該 role `kms:Decrypt`
- C. 將 gateway endpoint 改為 interface endpoint
- D. 在 NACL 開放 443 出站

> [!success]- 解答：**B**
> **為什麼對**：**`AccessDenied` 是權限問題，不是網路問題**。SSE-KMS 物件需要**兩層**授權：對 S3 的 `s3:GetObject` **與**對該 CMK 的 `kms:Decrypt`。
> **為什麼其他錯**：**A、C、D 全是網路層方案**——但網路若不通，症狀會是 **timeout** 而不是 403。這題在測「Timeout 找網路，403 找權限」的分流能力。
> **關聯**：[[EC2與IAM安全]]、[[威脅偵測與邊界防護]]、[[EC2與網路]]

## Q4
一家 SaaS 廠商需要 assume 你帳號中的一個 IAM role 來管理資源。安全團隊擔心該廠商可能被誘導存取其他客戶的資源。

- A. 在 role 的 trust policy 中加入 `sts:ExternalId` 條件
- B. 為廠商建立 IAM user 並發放 access key
- C. 使用 SCP 限制該 role
- D. 啟用 MFA

> [!success]- 解答：**A**
> **為什麼對**：這是教科書級的 **confused deputy（混淆代理人）**問題，標準解就是 **External ID**——只有知道這組雙方約定的字串才能成功 assume。
> **為什麼其他錯**：**B** 是長期憑證反模式。**C** SCP 是帳號層級權限上限，解決的不是這個攻擊向量。**D** MFA 適用於人類使用者，不適用於第三方程式化存取。
> **關聯**：[[身分聯合與應用存取]]

## Q5
需要掃描 S3 儲存貯體，找出其中是否含有身分證號、信用卡號等個人資料。

- A. Amazon GuardDuty
- B. Amazon Inspector
- C. Amazon Macie
- D. AWS Security Hub

> [!success]- 解答：**C**
> **記憶法**：**Macie 看資料內容（S3 裡有什麼）、Inspector 看運算資源漏洞（CVE）、GuardDuty 看威脅行為、Security Hub 做彙整。** 這四個是固定的干擾組合，背熟就穩拿分。
> **關聯**：[[威脅偵測與邊界防護]]

## Q6
應用架構是 `NLB → EC2`。安全團隊要求必須阻擋 SQL injection 與 XSS 攻擊。

- A. 直接在 NLB 上附加 AWS WAF
- B. 在 EC2 的 Security Group 上設定規則
- C. 在 NLB 前方加上 CloudFront 並附加 AWS WAF
- D. 啟用 AWS Shield Standard

> [!success]- 解答：**C**
> **為什麼對**：**WAF 掛不上 NLB**。可掛載的資源是 CloudFront、ALB、API Gateway、AppSync、Cognito User Pool、App Runner、Verified Access。所以要嘛前面加 CloudFront，要嘛改用 ALB。
> **為什麼其他錯**：**A** 技術上不成立。**B** SG 只看端口與來源 IP，看不懂 HTTP 內容。**D** Shield 擋 L3/L4 DDoS，不是 L7 應用層攻擊。
> **關聯**：[[威脅偵測與邊界防護]]、[[EC2與負載平衡及擴展]]

## Q7
組織有 60 個 AWS 帳號。安全政策要求「**任何帳號都不得停用 CloudTrail**」，即使該帳號的管理員也不行。

- A. 在每個帳號的 IAM policy 加 Deny
- B. 在 Organizations 套用 SCP，Deny `cloudtrail:StopLogging`
- C. 使用 AWS Config 規則偵測並告警
- D. 使用 permission boundary

> [!success]- 解答：**B**
> **為什麼對**：**SCP 是權限天花板**，帳號內的管理員（包含該帳號的 IAM admin）都無法突破。這正是「連管理員也不行」的實作方式。
> **為什麼其他錯**：**A** 帳號管理員可自行改掉 IAM policy。**C** Config 是**偵測**（detective）不是**預防**（preventive），事後發現而非阻止。**D** permission boundary 是限制「該身分能建立的權限上限」，需逐一附加，不是組織級強制。
> **注意**：SCP **不適用於管理帳號**。
> **關聯**：[[治理與合規]]

## Q8
需要儲存資料庫密碼，要求**每 30 天自動輪替**且與 RDS 整合。

- A. Systems Manager Parameter Store（SecureString）
- B. AWS Secrets Manager
- C. 存在加密的 S3 物件中
- D. 存在 Lambda 環境變數

> [!success]- 解答：**B**
> **關鍵字**：**`automatic rotation` → Secrets Manager**。Parameter Store 沒有內建輪替（要自己寫 Lambda），但**免費**——若題目只說「安全存放組態且成本最低」則選 Parameter Store。這組比較非常常考。
> **關聯**：[[治理與合規]]

## Domain 2｜設計高韌性架構（26%）

## Q9
應用需要跨 Region 的關聯式資料庫，要求 **RPO 約 1 秒、RTO 約 1 分鐘**。

- A. RDS Multi-AZ 部署
- B. RDS 跨 Region read replica，災難時手動提升
- C. Aurora Global Database
- D. 每小時建立 RDS snapshot 並複製到另一 Region

> [!success]- 解答：**C**
> **為什麼對**：Aurora Global Database 的設計目標就是這組數字（典型複寫延遲 < 1 秒、跨 Region 提升約 1 分鐘）。
> **為什麼其他錯**：**A** Multi-AZ 是**同 Region** 跨 AZ，不是 DR。**B** 跨 Region read replica 的 RTO 取決於人工/腳本提升，達不到 1 分鐘的保證。**D** RPO 最差 1 小時，遠超要求。
> **關聯**：[[高可用備援與災難復原]]、[[資料庫與快取]]

## Q10
公司的 Web 應用部署在兩個 AZ 的 ASG 中。某次 AZ 故障時，**另一個 AZ 的私有子網實例也失去了對外網路連線**。

- A. 增加 ASG 的期望容量
- B. 在每個 AZ 各部署一個 NAT gateway，並讓各 AZ 私有路由表指向自己 AZ 的 NAT
- C. 將實例改放到公有子網
- D. 啟用 ALB 的 cross-zone load balancing

> [!success]- 解答：**B**
> **為什麼對**：**NAT gateway 是 AZ 級資源**。若所有私有子網都指向單一 AZ 的 NAT，該 AZ 故障會讓**全部** AZ 斷網。每 AZ 一個 NAT 同時解決可用性與跨 AZ 傳輸費。
> **為什麼其他錯**：**A** 容量不是問題。**C** 違反安全設計。**D** cross-zone 影響流量分配，與出站網路無關。
> **關聯**：[[EC2與網路]]、[[成本與可觀測性]]

## Q11
訂單系統的下游有三個服務（出貨、通知、分析）都需要處理**同一筆訂單事件**。其中分析服務經常變慢，但不能因此影響出貨。

- A. 由應用程式依序呼叫三個服務的 API
- B. 發布到 SNS topic，三個服務各自訂閱一個 SQS queue，各自有 DLQ
- C. 發布到單一 SQS queue，三個服務共同消費
- D. 用 Step Functions 依序編排三個服務

> [!success]- 解答：**B**
> **為什麼對**：這是 **SNS fan-out + 每消費者一個 SQS 緩衝**的標準形狀。每個下游有獨立的佇列、獨立的處理速度、獨立的重試與 DLQ，彼此完全隔離。
> **為什麼其他錯**：**A** 同步呼叫 = 緊耦合，分析變慢會拖垮整條鏈。**C** **單一 SQS 的訊息被一個消費者取走後其他人就看不到了**，做不到三方都收到——這是 SQS 與 SNS 最核心的差別。**D** Step Functions 是編排，仍是耦合的，且不解決速度隔離問題。
> **關聯**：[[事件驅動與無伺服器]]

## Q12
ASG 中的實例上，應用程式當掉了（process 死亡），但作業系統仍正常運作。ASG **沒有替換**這台實例。

- A. 增加 ASG 的最小容量
- B. 將 ASG 的 health check type 從 EC2 改為 ELB
- C. 縮短 ALB 健康檢查的間隔
- D. 啟用 detailed monitoring

> [!success]- 解答：**B**
> **為什麼對**：ASG 的 health check type **預設是 `EC2`**，只看 instance status check（硬體/OS 層）。應用掛了但 OS 活著時 ASG 不會動作。改為 **ELB** 後，ASG 會依 target group 的健康狀態替換實例。
> **為什麼其他錯**：**C** ALB 會停止導流，但**不會替換實例**——替換是 ASG 的職責。**A、D** 無關。
> **關聯**：[[EC2與負載平衡及擴展]]、[[運算與容器選型]]

## Q13
公司要防範勒索軟體：備份資料必須**即使管理員或 root 帳號也無法刪除**，保留 7 年。

- A. 啟用 S3 Versioning 與 MFA Delete
- B. 使用 S3 Object Lock 的 Compliance mode（或 AWS Backup Vault Lock 的合規模式）
- C. 將備份複製到另一個帳號的 S3
- D. 啟用 S3 Glacier Deep Archive

> [!success]- 解答：**B**
> **為什麼對**：**Compliance mode 是唯一「連 root 都不能刪改」**的機制。Governance mode 允許特權使用者繞過，所以不符合題意。
> **為什麼其他錯**：**A** MFA Delete 提高門檻但擁有 MFA 的 root 仍可刪。**C** 跨帳號增加隔離但目標帳號管理員仍可刪。**D** 儲存類別與可刪除性無關。
> **關聯**：[[S3與資料生命週期]]、[[治理與合規]]

## Q14
一個批次工作目前由單台 EC2 執行，處理時間約 40 分鐘。團隊想改成無伺服器以降低維運負擔。

- A. 改用 AWS Lambda
- B. 改用 AWS Fargate（ECS 或 Batch）
- C. 改用 API Gateway + Lambda
- D. 改用較小的 EC2 instance

> [!success]- 解答：**B**
> **為什麼對**：**Lambda 最長 15 分鐘**，40 分鐘直接出局。無伺服器且不受此限的選項是 **Fargate**（可搭配 AWS Batch 做批次排程）。
> **教訓**：題幹裡的**時間數字就是篩選器**。看到執行時間先對照 15 分鐘這條線。
> **關聯**：[[運算與容器選型]]、[[數字與門檻速查]]

## Q15
SQS 佇列中的訊息**被處理了多次**，導致重複出貨。處理一筆訊息平均需要 90 秒。

- A. 改用 FIFO 佇列
- B. 將 visibility timeout 從 30 秒調高到超過處理時間
- C. 啟用 long polling
- D. 增加 worker 數量

> [!success]- 解答：**B**
> **為什麼對**：visibility timeout **預設 30 秒**，但處理要 90 秒——訊息在處理完成前就重新可見，被另一個 worker 取走。調高到大於處理時間（例如 180 秒）即可。
> **為什麼其他錯**：**A** FIFO 提供去重，但成本是吞吐量下降，而且**沒有解決根本原因**（timeout 太短）；題目也沒提到順序需求。**C** long polling 是降低空回應與成本，與重複無關。**D** 更多 worker 只會讓重複更嚴重。
> **補充**：即使調整了 timeout，**consumer 仍應設計為冪等**——SQS Standard 本來就是「至少一次」傳遞。
> **關聯**：[[事件驅動與無伺服器]]

## Q16
需要在 Region 故障時於**數秒內**把流量切到備援 Region，且客戶端的防火牆只允許連到**固定 IP**。

- A. Route 53 failover routing policy 搭配較短的 TTL
- B. AWS Global Accelerator
- C. CloudFront 搭配 origin group
- D. 跨 Region 的 ALB

> [!success]- 解答：**B**
> **為什麼對**：兩個條件各自指向 GA——**固定 anycast IP**（Route 53 給的是 DNS 名稱不是固定 IP）與**秒級切換**（不受 DNS TTL 與客戶端快取影響）。
> **為什麼其他錯**：**A** DNS 切換受 TTL 與各層 resolver 快取影響，做不到保證秒級，也不提供固定 IP。**C** CloudFront origin group 處理的是 origin 故障，且 CloudFront 主要針對 HTTP 快取。**D** ALB 是 Region 內資源。
> **關聯**：[[DNS與全球流量]]、[[高可用備援與災難復原]]

## Domain 3｜設計高效能架構（24%）

## Q17
兩個 AZ 的 Linux EC2 需要**同時讀寫同一個目錄**，應用使用標準 POSIX 檔案操作，不打算修改程式碼。

- A. 將 EBS volume 使用 Multi-Attach 掛載到兩台實例
- B. Amazon EFS
- C. Amazon S3
- D. Amazon FSx for Windows File Server

> [!success]- 解答：**B**
> **為什麼對**：EFS = 跨 AZ 的託管 NFS，原生 POSIX 語意，不需改程式碼。
> **為什麼其他錯**：**A** EBS Multi-Attach **僅限 io1/io2、同一 AZ**，且需要 cluster-aware 檔案系統；用一般 ext4/XFS 會毀損資料。**C** S3 是物件 API，**不是 POSIX**，需要改程式碼。**D** FSx for Windows 是 SMB，給 Windows 用。
> **關聯**：[[EC2與儲存]]

## Q18
DynamoDB 的讀取延遲需要降到**微秒等級**，且希望**幾乎不修改應用程式碼**。

- A. ElastiCache for Redis
- B. DynamoDB Accelerator（DAX）
- C. 啟用 DynamoDB 強一致性讀取
- D. 增加 provisioned read capacity

> [!success]- 解答：**B**
> **為什麼對**：DAX 是 DynamoDB **專用**的寫穿透快取，API 相容，應用幾乎不用改，延遲微秒級。
> **為什麼其他錯**：**A** ElastiCache 可行但需要應用自行管理快取邏輯（改程式碼）。**C** 強一致讀**更慢更貴**。**D** 增加容量解決限流，不解決延遲下限。
> **關聯**：[[資料庫與快取]]

## Q19
機器學習訓練需要從 S3 讀取數百 TB 資料，要求**極高吞吐的平行檔案系統**存取。

- A. Amazon EFS
- B. Amazon FSx for Lustre
- C. Amazon EBS io2
- D. S3 Transfer Acceleration

> [!success]- 解答：**B**
> **為什麼對**：**`HPC` / `machine learning` + `high performance file system` + 與 S3 連動 → FSx for Lustre**。它可以直接連結 S3 儲存貯體並延遲載入資料。
> **為什麼其他錯**：**A** EFS 吞吐不及 Lustre，不是為 HPC 設計。**C** EBS 是單實例區塊儲存。**D** Transfer Acceleration 加速的是上傳到 S3，不是運算時的檔案存取。
> **關聯**：[[EC2與儲存]]

## Q20
資料分析團隊要對 S3 上的 CSV 日誌做**臨時性 SQL 查詢**，查詢頻率低，不想維護任何叢集。目前查詢很慢且費用偏高。

- A. 建立 Redshift 叢集並載入資料
- B. 使用 Athena，並將資料轉為 Parquet、壓縮並依日期分區
- C. 啟動 EMR 叢集執行 Hive
- D. 將資料載入 RDS

> [!success]- 解答：**B**
> **為什麼對**：`ad-hoc`、`infrequent`、`no cluster to manage` → **Athena**。而 Athena **按掃描資料量計費**，所以效能與成本的標準解法就是**列式格式 + 壓縮 + 分區**這三件事。
> **為什麼其他錯**：**A、C** 都要維護叢集，違反題意，且低頻查詢下成本更高。**D** RDS 是 OLTP，不適合大規模分析。
> **關聯**：[[資料分析與串流]]

## Q21
全球使用者上傳大型影片到位於東京 Region 的單一 S3 儲存貯體，歐美使用者的上傳速度非常慢。

- A. 在每個 Region 建立 bucket 並做跨 Region 複寫
- B. 啟用 S3 Transfer Acceleration
- C. 啟用 CloudFront 並將 S3 設為 origin
- D. 改用 S3 Intelligent-Tiering

> [!success]- 解答：**B**
> **為什麼對**：Transfer Acceleration 讓使用者先連到就近的 CloudFront edge，再經 AWS 骨幹網路傳到目標 bucket——**專門解決長距離上傳慢**的問題。
> **為什麼其他錯**：**A** 增加大量複雜度與成本，且使用者仍需知道要傳到哪個 bucket。**C** CloudFront 主要加速**下載**（快取），不加速上傳。**D** 儲存類別與傳輸速度無關。
> **關聯**：[[S3與資料生命週期]]

## Q22
一個 Lambda 函式在高併發時，RDS 資料庫回報 `too many connections` 錯誤。

- A. 增加 RDS instance 的規格
- B. 建立 RDS Proxy 並讓 Lambda 透過它連線
- C. 增加 Lambda 的記憶體配置
- D. 建立 read replica

> [!success]- 解答：**B**
> **為什麼對**：問題在**連線數**不在運算量。**RDS Proxy 提供連線池**，把大量短生命週期的 Lambda 連線收斂成少量對 DB 的持久連線。這是近年高頻題。
> **為什麼其他錯**：**A** 加大規格能提高連線上限但治標且昂貴。**C** 記憶體與連線數無關。**D** read replica 分攤讀取，但寫入仍走主庫，且連線問題依舊。
> **關聯**：[[資料庫與快取]]

## Q23
即時點擊流資料需要同時被**三個不同團隊**各自處理，且其中一個團隊需要**重跑過去 3 天的資料**。

- A. Amazon SQS
- B. Amazon Kinesis Data Streams，保留期設為 7 天
- C. Amazon Data Firehose 直接寫入 S3
- D. Amazon SNS

> [!success]- 解答：**B**
> **為什麼對**：兩個條件都指向 Data Streams——**多個獨立 consumer 各自讀同一份資料並維護自己的 position**，以及**可重播保留期內的歷史資料**（保留期最長 365 天）。
> **為什麼其他錯**：**A** SQS 訊息被取走即消失，無法多方各自消費，也無法重播。**C** Firehose 送出即結束，沒有重播能力，也不是即時。**D** SNS 可 fan-out 但**不保留歷史、無法重播**。
> **關聯**：[[資料分析與串流]]

## Q25
一批資料需要保存 **45 天**後刪除，期間**不會被存取**，要求成本最低。

- A. S3 Glacier Flexible Retrieval
- B. S3 Glacier Deep Archive
- C. S3 Standard-IA
- D. S3 One Zone-IA

## Domain 1｜設計安全架構（Q31–Q39）

## Q31
營運團隊需要登入位於私有子網的 EC2 進行疑難排解。安全政策**禁止開啟任何入站端口**，也不允許維護堡壘主機（bastion host）。

- A. 在公有子網建立 bastion host，只允許公司 IP 連入 22 port
- B. 使用 Systems Manager Session Manager
- C. 為 EC2 指派 Elastic IP 並限制 Security Group 來源
- D. 設定 Site-to-Site VPN 後直接 SSH

> [!success]- 解答：**B**
> **為什麼對**：Session Manager 透過 SSM Agent **主動對外建立連線**，因此**完全不需要入站規則、不需要 SSH key、不需要 bastion**，且所有工作階段可記錄到 S3/CloudWatch 供稽核。題幹的兩個禁令直接指向它。
> **為什麼其他錯**：**A** 題目明說不允許 bastion。**C** 指派 EIP 等於把實例暴露到網際網路，且仍要開 22。**D** VPN 解決了網路可達性，但**仍需要在 EC2 上開啟 22 入站**，違反第一個禁令。
> **前提條件**（Lab 會踩到）：SSM Agent、帶 `AmazonSSMManagedInstanceCore` 的 instance profile、到 SSM API 的網路路徑（NAT 或 `ssm`/`ssmmessages`/`ec2messages` 三個 interface endpoint）。
> **關聯**：[[治理與合規]]、[[實作路線]] Lab D

## Q32
公司有 50 個 AWS 帳號，員工使用既有的 on-premises Active Directory 帳號。要求員工能以單一身分登入各帳號的主控台，且**不在每個帳號建立 IAM user**。

- A. 在每個帳號建立 IAM user 並啟用 MFA
- B. 在每個帳號建立 IAM role，各自設定 SAML 信任關係
- C. 啟用 IAM Identity Center，串接 AD 作為身分來源，用 permission set 指派權限
- D. 使用 Amazon Cognito User Pool

> [!success]- 解答：**C**
> **為什麼對**：**員工 × 多帳號 × 既有 IdP = IAM Identity Center**。permission set 一次定義、指派到「使用者/群組 × 帳號」的組合，背後自動在目標帳號建立 role。
> **為什麼其他錯**：**A** 直接違反題意，且 50 個帳號的 IAM user 是維運災難。**B** 技術上可行，但要手動維護 50 組 SAML 信任——這是典型的「可行但維運負擔高」干擾項。**D** **Cognito 是給 App 終端使用者的，不是員工**。Cognito 與 Identity Center 的混淆是高頻失分點。
> **關聯**：[[身分聯合與應用存取]]

## Q33
金融法規要求加密金鑰必須存放在**單租戶的專用硬體**中，且通過 **FIPS 140-3 Level 3** 驗證，AWS 不得有能力存取金鑰。

- A. AWS KMS 客戶管理金鑰（CMK）並啟用自動輪替
- B. AWS CloudHSM
- C. KMS 搭配匯入的金鑰材料（BYOK）
- D. Secrets Manager

> [!success]- 解答：**B**
> **關鍵字對應**：`single-tenant` + `dedicated hardware` + `FIPS 140-3 Level 3` + `AWS must not have access` → **CloudHSM**，沒有第二個選項。
> **為什麼其他錯**：**A** KMS 是**多租戶**託管服務。**C** BYOK 讓你控制金鑰材料來源，但**金鑰仍存放在 KMS 的多租戶 HSM 中**，不符合單租戶要求——這是最刁鑽的干擾項。**D** Secrets Manager 存的是密鑰值不是加密金鑰，且底層仍用 KMS。
> **代價提醒**：CloudHSM 維運負擔與成本都遠高於 KMS。**沒有出現上述法規字眼時不要選它。**
> **關聯**：[[威脅偵測與邊界防護]]

## Q34
一個 S3 儲存貯體需要提供公開靜態網站。團隊已設定允許 `s3:GetObject` 給 `Principal: "*"` 的 bucket policy，但存取仍回傳 403。

- A. bucket policy 語法錯誤
- B. 儲存貯體或帳號層級啟用了 S3 Block Public Access
- C. 物件使用 SSE-KMS 加密
- D. 缺少 VPC endpoint

> [!success]- 解答：**B**
> **為什麼對**：**Block Public Access 的優先序高於任何 bucket policy 與 ACL**。只要它開著，再寬鬆的 policy 都無效。這是 S3 排錯題的第一個檢查點。
> **為什麼其他錯**：**A** 題幹已說明 policy 設定內容。**C** SSE-KMS 確實會造成 403，但**匿名公開存取本來就無法取得 KMS 權限**，這情境下題目要考的是更前面那一關。**D** 公開網際網路存取不需要 VPC endpoint。
> **延伸**：實務上**不應該**為了靜態網站而關閉 Block Public Access，正解架構是 **CloudFront + OAC 保持 bucket 私有**。
> **關聯**：[[S3與資料生命週期]]、[[DNS與全球流量]]

## Q35
安全團隊希望允許開發人員**自行建立 IAM role** 給他們的應用使用，但要確保**開發人員建立出來的 role 權限不能超過特定範圍**（例如不能有 `iam:*` 或 `organizations:*`）。

- A. 套用 SCP 到該帳號
- B. 為開發人員的 IAM 身分附加 permission boundary，並要求他們建立 role 時必須附加同一個 boundary
- C. 使用 IAM Access Analyzer 定期掃描
- D. 移除開發人員建立 role 的權限

> [!success]- 解答：**B**
> **為什麼對**：**permission boundary 正是為「委派 IAM 管理權但設上限」而設計**。透過條件式 policy 強制開發人員建立的 role 必須帶上指定 boundary，就能保證衍生的 role 權限不超界。
> **為什麼其他錯**：**A** SCP 作用在**整個帳號或 OU**，會一併限制該帳號所有身分（包含管理員與現有工作負載），粒度不對。**C** Access Analyzer 是**偵測**不是**預防**。**D** 完全禁止，但題目要的是「允許他們建立」。
> **對照記憶**：**SCP = 帳號/OU 的天花板；permission boundary = 單一身分的天花板。**
> **關聯**：[[身分聯合與應用存取]]、[[治理與合規]]

## Q36
稽核要求：組織內**所有帳號的 EBS volume 都必須加密**，違規者要被記錄並**自動修正**。

- A. 使用 CloudTrail 監控 `CreateVolume` API
- B. 使用 AWS Config 規則 `encrypted-volumes`，搭配 SSM Automation 作為 remediation action，並以 conformance pack 部署到所有帳號
- C. 使用 CloudWatch alarm 監控 EBS 指標
- D. 使用 Trusted Advisor 檢查

> [!success]- 解答：**B**
> **為什麼對**：**「資源設定是否符合規範」+「自動修正」= AWS Config + remediation**。conformance pack 與 Config aggregator 處理跨帳號部署與彙整。
> **為什麼其他錯**：**A** CloudTrail 記錄「誰做了什麼」，能事後追查但**不評估合規狀態也不會修正**。**C** CloudWatch 看效能指標，看不到加密屬性。**D** Trusted Advisor 檢查項目固定，不能自訂規則也不會自動修正。
> **記憶法**：**CloudTrail 記錄動作、Config 記錄狀態、CloudWatch 記錄表現。** 題目問「合規/組態偏移」一律先想 Config。
> **關聯**：[[治理與合規]]

## Q37
團隊在 `ap-northeast-1`（東京）簽發了 ACM 憑證，想套用到 CloudFront distribution，但在主控台的憑證下拉選單中找不到它。

- A. 憑證尚未驗證完成
- B. CloudFront 使用的 ACM 憑證必須簽發在 `us-east-1`
- C. CloudFront 不支援 ACM，必須自行上傳憑證
- D. 需要先啟用 SNI

> [!success]- 解答：**B**
> **為什麼對**：這是一條沒有道理可講、但必須記住的硬規則——**CloudFront 只讀取 `us-east-1`（維吉尼亞北部）的 ACM 憑證**。ALB 則使用**與 ALB 同 Region** 的憑證。
> **為什麼其他錯**：**A** 未驗證的憑證會顯示但不可選，且題目描述是「找不到」。**C** CloudFront 原生整合 ACM。**D** SNI 是 ALB 掛多憑證的機制，與此無關。
> **關聯**：[[DNS與全球流量]]、[[數字與門檻速查]]

## Q38
S3 跨 Region 複寫（CRR）已設定完成，來源物件使用 **SSE-KMS** 加密。複寫任務持續失敗。

- A. 目的地儲存貯體未啟用版本控制
- B. 複寫角色缺少對來源金鑰的 `kms:Decrypt` 與對目的地 Region 金鑰的 `kms:Encrypt`（或改用 multi-Region key）
- C. 來源與目的地在不同帳號
- D. 需要啟用 S3 Transfer Acceleration

> [!success]- 解答：**B**
> **為什麼對**：**KMS CMK 是 Region 專屬的**。跨 Region 複寫加密物件時，複寫角色必須能**在來源 Region 解密**、**在目的地 Region 加密**。解法是明確授予兩邊金鑰權限，或使用 **multi-Region key**。
> **為什麼其他錯**：**A** 這確實是 CRR 的必要條件，但若未啟用，複寫**根本無法設定**而不是「設定完成後失敗」——題幹已說設定完成。**C** 跨帳號複寫是支援的。**D** 與複寫無關。
> **通用結論**：看到「**跨 Region + 加密**」的組合，**一律先想目的地 Region 的金鑰問題**。Aurora Global Database、EBS snapshot 跨 Region 複製都有同樣的坑。
> **關聯**：[[威脅偵測與邊界防護]]、[[S3與資料生命週期]]

## Q39
部署在 ECS Fargate 上的服務無法啟動，事件記錄顯示**無法從 Amazon ECR 拉取容器映像**。

- A. Task role 缺少 ECR 權限
- B. Task execution role 缺少 ECR 權限
- C. 容器內的應用程式缺少 IAM 權限
- D. Security Group 未開放 ECR 端口

> [!success]- 解答：**B**
> **為什麼對**：**拉取映像、寫 CloudWatch Logs、從 Secrets Manager 注入環境變數，都是「基礎設施代表你做的事」，用的是 task execution role。**
> **為什麼其他錯**：**A、C** **task role 是給容器內應用程式呼叫 AWS API 用的**（讀 S3、寫 DynamoDB），與拉映像無關。這組角色混淆是 ECS 最經典的考點。**D** 網路問題的症狀通常是 timeout；且 Fargate 在私有子網拉 ECR 映像確實需要 NAT 或 `ecr.api`/`ecr.dkr`/`s3` endpoint——但題目若要考網路會描述成逾時。
> **一句話**：**啟動失敗拉不到映像 → execution role；執行中 403 → task role。**
> **關聯**：[[運算與容器選型]]

## Domain 2｜設計高韌性架構（Q40–Q47）

## Q40
全球性應用需要讓**美國與歐洲的使用者都能在本地讀寫**同一份 NoSQL 資料，且任一 Region 故障時另一邊能繼續服務。

- A. DynamoDB 搭配跨 Region 的 read replica
- B. DynamoDB Global Tables
- C. 在兩個 Region 各建一張獨立的 DynamoDB 表，由應用程式同步
- D. Aurora Global Database

> [!success]- 解答：**B**
> **為什麼對**：Global Tables 提供**多 Region active-active 寫入**，複寫延遲通常在秒級，衝突以**最後寫入者勝**解決。「兩地都要能寫」是它與其他方案的分水嶺。
> **為什麼其他錯**：**A** DynamoDB **沒有「read replica」這個概念**，這是把 RDS 詞彙套到 DynamoDB 的假選項——要小心這類「名詞張冠李戴」的干擾。**C** 自行同步等於重造 Global Tables 且容易出錯。**D** Aurora 是**關聯式**資料庫，題目說 NoSQL。
> **關聯**：[[資料庫與快取]]、[[高可用備援與災難復原]]

## Q41
生產環境的 RDS MySQL 需要在**單一 AZ 故障時自動切換**，停機時間最短，且**不需要額外的讀取容量**。

- A. 建立 read replica 並在故障時手動提升
- B. 啟用 Multi-AZ 部署
- C. 每 5 分鐘建立一次 snapshot
- D. 在另一個 Region 建立跨 Region read replica

> [!success]- 解答：**B**
> **為什麼對**：`automatic failover` + `AZ failure` + `不需要讀取擴展` → **Multi-AZ DB instance**。standby 同步複寫，故障時 DNS endpoint 自動指向新的主庫。
> **為什麼其他錯**：**A** read replica 是**非同步**複寫且**不會自動切換**，且題目明說不需要額外讀取容量。**C** snapshot 是備份，RPO 與 RTO 都遠差於 Multi-AZ。**D** 跨 Region 是 DR 方案，對「AZ 故障」是過度設計且不會自動切換。
> **鐵律再記一次**：**Multi-AZ 是 HA、Read Replica 是讀取擴展、跨 Region 是 DR。三者不可互換。**
> **關聯**：[[資料庫與快取]]

## Q42
ASG 在縮容時終止實例，但團隊發現**實例上的應用日誌來不及上傳就消失了**。

- A. 增加 ASG 的冷卻時間（cooldown）
- B. 設定 ASG lifecycle hook，在 `Terminating` 狀態暫停並上傳日誌
- C. 停用 scale-in
- D. 改用 detailed monitoring

> [!success]- 解答：**B**
> **為什麼對**：**lifecycle hook 讓實例在 `Pending` 或 `Terminating` 狀態暫停**，給你時間做初始化或優雅排空/擷取日誌，完成後再送出 `CompleteLifecycleAction`。
> **為什麼其他錯**：**A** cooldown 控制的是**兩次擴縮動作之間的間隔**，不會延後單一實例的終止。**C** 停用 scale-in 等於放棄成本效益，且是逃避問題。**D** 監控粒度與此無關。
> **延伸**：更好的長期解是**用 CloudWatch Agent 即時串流日誌**，讓日誌根本不依賴實例存活。題目若同時給這兩個選項，看題幹強調「立即修正」還是「架構改善」。
> **關聯**：[[運算與容器選型]]、[[EC2與負載平衡及擴展]]

## Q43
一個既有的 Java 應用使用 **JMS** 與 message broker 溝通。公司要把它搬到 AWS，要求**不修改應用程式碼**。

- A. Amazon SQS
- B. Amazon SNS
- C. Amazon MQ
- D. Amazon Kinesis Data Streams

> [!success]- 解答：**C**
> **為什麼對**：**Amazon MQ 支援業界標準協定（JMS、AMQP、MQTT、STOMP、OpenWire）**，應用只要改連線字串就能運作。`existing application` + `message broker` + `no code change` 是它在考試中幾乎唯一的正解情境。
> **為什麼其他錯**：**A、B、D 全都是 AWS 專有 API**，必須改寫應用程式碼，直接違反題意。
> **反向提醒**：**如果題目是全新開發**（沒有「既有」「不改程式碼」的字眼），答案通常是 **SQS**——它擴展性更好、維運負擔更低、更便宜。看到 Amazon MQ 就要確認題幹真的有「既有系統」的條件。
> **關聯**：[[事件驅動與無伺服器]]、[[資料分析與串流]]

## Q44
金融交易訊息必須**嚴格依照送出順序處理**，且**絕對不能重複處理**。

- A. SQS Standard queue 搭配應用層去重
- B. SQS FIFO queue，使用相同的 message group ID
- C. SNS topic
- D. EventBridge

> [!success]- 解答：**B**
> **為什麼對**：`order must be preserved` + `no duplicates` 這兩個詞同時出現 → **FIFO**。FIFO 在同一 message group 內保證順序，並提供 5 分鐘去重窗達成 exactly-once 處理。
> **為什麼其他錯**：**A** Standard 是 at-least-once 且**不保證順序**；應用層去重能解決重複但解決不了順序。**C** SNS 標準 topic 不保證順序。**D** EventBridge 不保證順序。
> **代價提醒**：FIFO 吞吐量低於 Standard。**題目沒提到順序或重複就不要選 FIFO**——那是過度設計。
> **仍要注意**：即使用了 FIFO，跨 message group 之間**沒有**順序保證，consumer 仍應設計為冪等。
> **關聯**：[[事件驅動與無伺服器]]

## Q45
公司在多個帳號中有 EBS、RDS、DynamoDB、EFS 資源，需要用**單一套政策**統一管理備份排程與保留期，並**複製到另一個 Region**。

- A. 為每種服務各自寫 Lambda 排程 snapshot
- B. AWS Backup，建立 backup plan 並設定跨 Region 複製
- C. 使用 Data Lifecycle Manager
- D. 使用 AWS Config 規則

> [!success]- 解答：**B**
> **為什麼對**：`centralized` + `multiple services` + `multiple accounts` + `cross-region copy` → **AWS Backup**。它就是為取代「每個服務各寫一套 snapshot 腳本」而生的。
> **為什麼其他錯**：**A** 維運負擔極高，是典型的「可行但最差」選項。**C** **Data Lifecycle Manager 只管 EBS snapshot 與 AMI**，涵蓋不了 RDS/DynamoDB/EFS。**D** Config 管合規不管備份。
> **延伸**：若題目再加上「備份不可被刪除」→ **AWS Backup Vault Lock（合規模式）**。
> **關聯**：[[治理與合規]]、[[高可用備援與災難復原]]

## Q46
災難復原需求：**RTO 4 小時、RPO 1 小時**，且要求**持續成本最低**。應用是標準的三層式架構。

- A. Multi-site active/active：兩個 Region 都全量運行
- B. Warm standby：在第二 Region 運行縮小版的完整環境
- C. Pilot light：只保持資料庫持續複寫，運算層以 CloudFormation 範本待命，災難時才啟動並擴展
- D. Backup & restore：只保留跨 Region 備份，災難時從頭重建

> [!success]- 解答：**C**
> **為什麼對**：解題順序是**先用 RTO 篩選，再在合格者中選最便宜**。
> RTO 4 小時相當寬鬆——pilot light 從範本啟動並擴展運算層通常在此範圍內；RPO 1 小時由持續的資料庫複寫滿足。在滿足條件的方案中 pilot light 的常駐成本最低。
> **為什麼其他錯**：**A、B** 都能達標但**持續成本明顯更高**，違反「成本最低」。**D** backup & restore 的 RTO 通常是數小時到一天，**4 小時內從零重建整個三層架構風險太高**，且 RPO 取決於備份頻率，較難保證 1 小時。
> **最常見的失分方式**：看到 `disaster recovery` 就反射選 active/active。**DR 題永遠是「在滿足 RTO/RPO 的前提下選最便宜的」。**
> **關聯**：[[高可用備援與災難復原]]

## Q47
Lambda 函式由 S3 事件**非同步**觸發。團隊發現處理失敗的事件**直接消失了**，無法得知哪些檔案沒被處理。

- A. 增加 Lambda 的 timeout
- B. 為 Lambda 設定 DLQ 或 Lambda Destinations（on-failure）
- C. 改用同步呼叫
- D. 啟用 X-Ray 追蹤

> [!success]- 解答：**B**
> **為什麼對**：**Lambda 非同步呼叫預設只重試 2 次，之後事件就被丟棄。** 要保留失敗事件必須明確設定 **DLQ（SQS/SNS）** 或 **Destinations 的 on-failure 目標**。
> **為什麼其他錯**：**A** timeout 只解決「執行太久」這一種失敗原因，不解決事件遺失。**C** S3 事件通知本質上是非同步的，無法改為同步。**D** X-Ray 幫助診斷但**不會保留事件本身**。
> **關聯**：[[事件驅動與無伺服器]]

## Domain 3｜設計高效能架構（Q48–Q54）

## Q48
巨量資料工作負載需要對 40 TB 的日誌檔做**大型循序讀取**，重視吞吐量而非隨機 IOPS，且希望儲存成本最低。這些 volume 不作為開機碟。

- A. gp3
- B. io2 Block Express
- C. st1（吞吐量最佳化 HDD）
- D. instance store

> [!success]- 解答：**C**
> **為什麼對**：**循序大區塊讀寫 + 成本敏感 = HDD**。st1 就是為 big data、log processing、data warehouse 這類吞吐導向工作負載設計的，每 GB 成本遠低於 SSD。
> **為什麼其他錯**：**A** gp3 可行但 40 TB 的 SSD 成本高出許多，題目強調成本。**B** io2 是最貴的選項，適合高 IOPS 的關鍵資料庫，與「循序吞吐」需求錯配。**D** instance store 是暫存，資料會在停止/終止時消失，不能放持久資料。
> **必記限制**：**st1 與 sc1 都不能作為開機磁碟**——題幹特意說明「不作為開機碟」就是在暗示 HDD 是可選的。
> **關聯**：[[EC2與儲存]]

## Q49
HPC 模擬工作負載需要在一組 EC2 實例之間達成**最低網路延遲與最高每秒封包數**。

- A. Spread placement group
- B. Cluster placement group
- C. Partition placement group
- D. 把實例分散到三個 AZ

> [!success]- 解答：**B**
> **為什麼對**：**Cluster placement group 把實例擠在同一個 AZ 的鄰近硬體上**，提供最低延遲與最高頻寬，正是 HPC / 緊耦合運算的標準做法（通常再搭配 **EFA** 網路介面）。
> **為什麼其他錯**：**A** Spread 刻意分散到**不同**硬體，延遲反而增加——它的目的是降低相關性故障。**C** Partition 用於 HDFS/Kafka/Cassandra 這類拓樸感知的分散式系統。**D** 跨 AZ 一定增加延遲。
> **取捨**：Cluster 的代價是**全部在同一個 AZ，AZ 故障即全滅**。考題若同時要求低延遲與高可用，通常表示需求本身矛盾，要看題幹哪個是硬條件。
> **關聯**：[[運算與容器選型]]

## Q50
Web 應用部署在多 AZ 的 ASG 上。需要一個**共享的 session store**，要求支援**自動故障切換**，且 session 資料在節點重啟後不能遺失。

- A. ElastiCache for Memcached
- B. ElastiCache for Redis（啟用 Multi-AZ 與自動故障切換）
- C. 在每台 EC2 的本機記憶體中儲存 session
- D. 使用 ALB sticky session

> [!success]- 解答：**B**
> **為什麼對**：題幹有兩個關鍵字——**`automatic failover`** 與 **`資料不能遺失（持久化）`**。這兩項 **Memcached 都不支援**，只有 Redis/Valkey 有。
> **為什麼其他錯**：**A** Memcached 純記憶體、無複寫、無故障切換、無持久化。**C** 存本機就完全違背「共享」。**D** sticky session 讓使用者黏在同一節點，**節點故障時該使用者仍會掉 session**，且題目要的是 session store 而非流量分配策略。
> **一句話**：**看到 HA / persistence / failover / backup 任一個 → Redis。** Memcached 在 SAA 中很少是正解。
> **關聯**：[[資料庫與快取]]、[[EC2與負載平衡及擴展]]

## Q51
需要在 CDN edge 對每個請求做**簡單的 URL 重寫與 header 修改**，要求延遲最低、成本最低。每秒有數百萬次請求。

- A. Lambda@Edge
- B. CloudFront Functions
- C. 在 origin 的 ALB 上設定規則
- D. API Gateway 的請求轉換

> [!success]- 解答：**B**
> **為什麼對**：**CloudFront Functions 專為輕量的 header/URL 操作設計**，執行在 edge location、延遲次毫秒、成本約為 Lambda@Edge 的六分之一，適合超高請求量。
> **為什麼其他錯**：**A** Lambda@Edge 功能更強（可存取網路、執行時間更長、可操作 request/response body），但**延遲較高、成本較高**，對「簡單重寫」是過度設計。**C** 在 origin 處理代表請求已經穿過 CDN，失去 edge 處理的意義。**D** API Gateway 不在 CloudFront 的 edge 路徑上。
> **分界**：**簡單 header/URL 改寫 → CloudFront Functions；需要呼叫外部服務、處理 body、較長執行 → Lambda@Edge。**
> **關聯**：[[運算與容器選型]]、[[DNS與全球流量]]

## Q52
一個延遲敏感的 API 由 Lambda 支援。監控顯示**每天早上流量開始時，前幾百個請求的延遲特別高**，之後恢復正常。

- A. 設定 reserved concurrency
- B. 設定 provisioned concurrency
- C. 增加 Lambda 的 timeout
- D. 增加 Lambda 的記憶體配置

> [!success]- 解答：**B**
> **為什麼對**：這是典型的**冷啟動（cold start）**症狀。**Provisioned concurrency 預先初始化執行環境**並保持溫熱，消除冷啟動延遲。
> **為什麼其他錯**：**A** **reserved concurrency 是「保留額度並設上限」，用於隔離不同函式互相搶佔併發，不會預熱環境**——這兩個名詞的混淆是高頻考點。**C** timeout 與啟動延遲無關。**D** 增加記憶體會提升 CPU 因而縮短初始化時間，但**只是緩解不是解決**。
> **成本較低的替代**：若 runtime 是 Java/Python/.NET，可考慮 **SnapStart**（免費）。
> **關聯**：[[運算與容器選型]]

## Q53
DynamoDB 表在尖峰時段出現大量 `ProvisionedThroughputExceededException`，但 CloudWatch 顯示**整體的已耗用容量遠低於佈建容量**。

- A. 增加佈建的 read/write capacity
- B. partition key 基數過低造成熱分割區，應改用高基數的 partition key（或加入隨機/計算後綴分散）
- C. 啟用 DynamoDB Streams
- D. 改用強一致性讀取

> [!success]- 解答：**B**
> **為什麼對**：「**整體容量有剩但仍被限流**」是**熱分割區（hot partition）**的教科書症狀——流量集中在少數 partition key 上，單一分割區的容量上限先被打滿。解法是重新設計 partition key 提高基數。
> **為什麼其他錯**：**A** 整體容量已經有剩，加更多只是浪費錢，**不會解決分布不均**。**C** Streams 是變更擷取，與限流無關。**D** 強一致讀**消耗雙倍容量**，會讓情況更糟。
> **辨識訣竅**：題目刻意描述「整體用量低但仍限流」就是在指向資料分布問題，而不是容量問題。
> **關聯**：[[資料庫與快取]]

## Q54
營運團隊需要對數 TB 的應用日誌做**即時的全文檢索**，並提供**互動式儀表板**讓工程師排查問題。

- A. 將日誌存到 S3，用 Athena 查詢
- B. 將日誌透過 Data Firehose 送入 Amazon OpenSearch Service，使用 OpenSearch Dashboards
- C. 將日誌存入 Redshift
- D. 使用 CloudWatch Logs Insights

> [!success]- 解答：**B**
> **為什麼對**：`full-text search` + `interactive dashboards` + `log analytics` → **OpenSearch Service**。Firehose 是把 CloudWatch Logs 或應用日誌送進去的標準管線。
> **為什麼其他錯**：**A** Athena 適合**偶爾的臨時 SQL 查詢**，不是即時全文檢索，也不提供互動式儀表板。**C** Redshift 是結構化資料倉儲，不擅長非結構化日誌的全文檢索。**D** Logs Insights 能查詢但**功能與儀表板能力遠不及 OpenSearch**；題目強調「即時全文檢索 + 儀表板」時 OpenSearch 是標準答案。
> **成本對照**：若題幹改成「**偶爾**查詢、**成本最低**」→ 答案會變成 **S3 + Athena**。兩者的分界在查詢頻率與即時性。
> **關聯**：[[資料分析與串流]]

## Domain 4｜設計成本最佳化架構（Q55–Q60）

## Q55
公司要把地端的 Oracle Database 搬到 EC2，並沿用既有的 **Oracle 授權**。該授權是**按實體 CPU socket 計算**的。

- A. Dedicated Instances
- B. Dedicated Hosts
- C. Reserved Instances
- D. 標準 On-Demand Instances

> [!success]- 解答：**B**
> **為什麼對**：**只有 Dedicated Host 讓你看見並控制實體伺服器的 socket 與 core 數量**，這是 BYOL 按 socket/core 計算授權時的唯一可行選項。
> **為什麼其他錯**：**A** Dedicated Instance 保證硬體不與其他客戶共用（滿足隔離型合規），但**你看不到底層的 socket/core 資訊**，無法據以計算授權。這組是最容易混淆的一對。**C、D** 是購買模式，與硬體可見性無關。
> **記憶法**：**看到 `BYOL` / `per-socket` / `per-core licensing` → Dedicated Host；只說「不與其他客戶共用硬體」→ Dedicated Instance 就夠。**
> **關聯**：[[運算與容器選型]]

## Q56
公司要把 **10 TB** 的歸檔資料從地端搬到 S3。資料中心有一條**閒置的 1 Gbps 專線**，可用時間為一週。要求成本最低且維運最簡單。

- A. 訂購 AWS Snowball Edge 裝置
- B. 使用 AWS DataSync 透過既有專線傳輸
- C. 使用 AWS Snowmobile
- D. 用 AWS CLI 寫腳本逐檔上傳

> [!success]- 解答：**B**
> **為什麼對**：先算一下——10 TB ≈ 80,000 Gb，在 1 Gbps 下即使只達成一半的有效吞吐，也**不到兩天**就能傳完，遠在一週的期限內。既然頻寬足夠，**DataSync 就是最省事的選擇**（自動增量、完整性驗證、保留中繼資料）。
> **為什麼其他錯**：**A** Snowball 的裝置訂購、運送、上傳、回送流程通常要一到兩週，**在頻寬足夠時反而更慢也更麻煩**。**C** Snowmobile 是 EB 級方案（且已停售），對 10 TB 是荒謬的過度設計。**D** 腳本上傳缺乏增量、重試與驗證機制，維運負擔高。
> **這題的意義**：Q 系列裡大多數 Snow 題是「頻寬不足 → 選 Snowball」，**這題是反向驗證**——看到大資料量不要反射選 Snowball，**要先比對頻寬與時限**。
> **關聯**：[[遷移與混合雲]]

## Q57
開發測試環境需要一個共享的 Linux 檔案系統。資料**可以重新產生**，團隊只在上班時間使用，且**大部分檔案超過 30 天沒被存取**。要求成本最低。

- A. EFS Standard，不設定生命週期
- B. EFS One Zone，並設定生命週期管理在 30 天後轉入 Infrequent Access
- C. 多台 EC2 各自掛 EBS 並用 rsync 同步
- D. FSx for Lustre

> [!success]- 解答：**B**
> **為什麼對**：題幹給了三個降本訊號——**「資料可重新產生」**（可接受單 AZ 風險 → **One Zone**，約便宜一半）、**「大部分超過 30 天未存取」**（→ **生命週期轉 IA**）、**「開發測試環境」**（非關鍵）。三個條件疊起來就是這個組合。
> **為什麼其他錯**：**A** 沒有利用任何降本機制。**C** 自行同步的維運負擔高且不是真正的共享檔案系統。**D** FSx for Lustre 是 HPC 高效能方案，成本遠高於需求。
> **注意反向條件**：若題目說「這是生產環境的關鍵資料」，**One Zone 就不能選**——單 AZ 風險不可接受。
> **關聯**：[[EC2與儲存]]、[[S3與資料生命週期]]

## Q58
公司有 12 個 AWS 帳號分屬不同部門。財務部門希望**取得整體的用量折扣**、**讓閒置的 Reserved Instances 被其他帳號使用**，並且能**依部門歸屬成本**。

- A. 將所有資源合併到單一帳號
- B. 使用 AWS Organizations 的合併帳務，啟用 RI/Savings Plans 共享，並設定成本分配標籤
- C. 為每個帳號各自購買 Reserved Instances
- D. 使用 Cost Explorer 分別檢視每個帳號

> [!success]- 解答：**B**
> **為什麼對**：三個需求各自對應一項能力——**合併帳務**帶來跨帳號的用量級距折扣；**RI/SP 共享**讓某帳號未用滿的預留被組織內其他帳號自動套用；**成本分配標籤**提供部門層級的歸因（chargeback）。
> **為什麼其他錯**：**A** 破壞帳號隔離這個重要的安全與爆炸半徑邊界。**C** 各自購買就無法互相共享，浪費未用滿的部分。**D** Cost Explorer 提供檢視，但**不會帶來折扣也不會共享 RI**。
> **補充**：若不希望某個帳號的 RI 被別人用掉，可以**關閉該帳號的 RI 共享**。
> **關聯**：[[治理與合規]]、[[成本與可觀測性]]

## Q59
內部報表資料庫（PostgreSQL）**每天只在上班時段被使用數小時**，其餘時間幾乎完全閒置，但偶爾會有突發的大量查詢。要求成本最佳化且維運負擔最低。

- A. 使用固定規格的 RDS PostgreSQL，並在下班後手動停止
- B. Aurora Serverless v2
- C. 使用最大規格的 Aurora provisioned instance 以應付突發
- D. 改用 DynamoDB

> [!success]- 解答：**B**
> **為什麼對**：`intermittent` + `unpredictable spikes` + `idle most of the time` + `least operational overhead` → **Aurora Serverless v2**。容量以 ACU 為單位自動增減，閒置時縮到極低，突發時快速擴張，且不需要人工介入。
> **為什麼其他錯**：**A** 手動停止有維運負擔，且 RDS 停止**最多 7 天就會自動啟動**，需要額外自動化；也無法應付突發。**C** 為了偶發尖峰而全天佈建最大規格，是最貴的做法。**D** 換成 NoSQL 需要重寫應用與查詢，且報表型的複雜查詢正是關聯式資料庫的強項。
> **關聯**：[[資料庫與快取]]、[[運算與容器選型]]

## Q60
月度帳單持續上升。管理層要求找出**未被使用的資源**以及**規格過大的 EC2 實例**，並提出具體的縮減建議。

- A. AWS Budgets
- B. Trusted Advisor（閒置資源檢查）搭配 AWS Compute Optimizer（規格建議）
- C. Cost and Usage Report
- D. CloudWatch dashboards

> [!success]- 解答：**B**
> **為什麼對**：題目問的是**兩件事**，各自對應一個工具——**Trusted Advisor** 檢查閒置/低使用率資源（未掛載的 EBS、未關聯的 EIP、閒置的 ELB/RDS）；**Compute Optimizer** 依實際使用率給出 **right-sizing 建議**。
> **為什麼其他錯**：**A** Budgets 是**超標告警**，不會分析資源使用率。**C** CUR 提供最細的帳單明細，但**需要你自己分析**，不會主動給建議。**D** CloudWatch 呈現指標，不會給最佳化建議。
> **注意前提**：**Trusted Advisor 的完整檢查項目需要 Business 或 Enterprise Support 方案**——題目若強調「不升級支援方案」，答案可能只剩 Compute Optimizer。
> **關聯**：[[成本與可觀測性]]

## 第二輪的重點回顧

這 30 題集中在六組最容易失分的辨析：

| 辨析 | 分界 |
|---|---|
| **reserved vs provisioned concurrency** | 隔離額度 vs **預熱消除冷啟動** |
| **task role vs task execution role** | 應用呼叫 API vs **基礎設施拉映像/寫日誌** |
| **SCP vs permission boundary** | 帳號/OU 天花板 vs **單一身分天花板** |
| **Dedicated Instance vs Dedicated Host** | 硬體隔離 vs **可見 socket/core 供 BYOL** |
| **Redis vs Memcached** | **HA/持久化/備份** vs 純多執行緒快取 |
| **Trusted Advisor vs Compute Optimizer vs Budgets** | 閒置檢查 vs **規格建議** vs 超標告警 |

另外有三題（Q38 跨 Region 加密、Q53 熱分割區、Q56 頻寬夠不選 Snowball）考的是**反直覺**的判斷，值得重做。

## 答題後的動作

每一題（**包含答對的**）都問自己：
1. 我是**憑關鍵字反射**還是**憑理解**選的？

第 3 點最重要——**能做變形題才代表真的懂了**。把不確定的項目記進 [[模考與錯題模板]]。
