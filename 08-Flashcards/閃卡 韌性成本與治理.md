## 🛡 韌性與 DR

RPO 與 RTO 各是什麼？::**RPO = 可接受的最大資料遺失時間**；**RTO = 可接受的最大恢復時間**

四類 DR 策略由便宜到貴？::Backup & restore → Pilot light → Warm standby → Multi-site active/active

DR 題的解題順序？::**先用 RTO 篩掉達不到的，再在合格者中選最便宜的**——看到 DR 就選 active/active 是最常見錯誤

「RTO 4 小時、成本最低」→ 選哪個 DR 策略？::**Pilot light**（active/active 與 warm standby 屬過度設計）

三組不可互換的概念？::**Multi-AZ ≠ DR**（同 Region）、**Read Replica ≠ HA**（不自動切換）、**備份 ≠ 高可用**

`RPO near zero, active-active, multi-region writes` + NoSQL → 選什麼？::**DynamoDB Global Tables**

`RPO ≈ 1 秒、RTO ≈ 1 分鐘` + 關聯式 → 選什麼？::**Aurora Global Database**

「物件必須在 15 分鐘內出現在第二個 Region，且要有保證」→ 選什麼？::**S3 CRR + Replication Time Control（RTC）**

「秒級跨 Region 切換，客戶端不需重新解析 DNS」→ 選什麼？::**Global Accelerator**（Route 53 failover 受 TTL 與客戶端快取影響）

99.99% 可用性一年大約停機多久？::約 **52 分鐘**（99.9% 約 8.8 小時、99.999% 約 5 分鐘）

串聯元件的可用性怎麼算？::**相乘**（0.99 × 0.99 = 0.9801）——所以增加依賴會降低整體可用性

AWS Elastic Disaster Recovery（DRS）提供什麼？::持續區塊層複寫到 AWS，是 pilot light / warm standby 的託管實作

## 📬 訊息與解耦

「訊息被處理多次」最可能的原因？::**visibility timeout 短於實際處理時間**——調長到大於處理時間（並保持 consumer 冪等）

SQS visibility timeout 的預設與上限？::預設 **30 秒**，最長 **12 小時**

Long polling 最長等待多久？解決什麼？::**20 秒**；減少空回應與 API 呼叫，**降低成本**

SQS 訊息大小上限？超過怎麼辦？::**256 KB**，更大用 **S3 + Extended Client Library**（訊息只放指標）

SQS 訊息保留期的預設與上限？::預設 **4 天**，最長 **14 天**

什麼條件下才選 FIFO？::題幹出現 **`order must be preserved`** 或 **`no duplicates`**。沒提到就選 Standard（吞吐與成本較佳）

FIFO 的去重窗多長？::**5 分鐘**

「三個下游都要處理同一筆事件且彼此不能互相影響」→ 架構？
?
`事件 → SNS topic → 三個 SQS queue（各一訂閱）→ 各自 worker + DLQ`
單一 SQS 做不到——訊息被一個消費者取走後其他人就看不到了。

SNS 與 EventBridge 怎麼選？::單純廣播 → **SNS**；**依內容路由 / SaaS 整合 / AWS 服務狀態變化 / 事件重播 / 排程** → **EventBridge**

EventBridge 有而 SNS 沒有的能力？::**Archive & Replay**、schema registry、規則路由、Scheduler、SaaS 與 AWS 服務原生整合

Step Functions Standard 與 Express 的最長執行時間？::Standard **1 年**；Express **5 分鐘**

API Gateway 三種 API 怎麼選？::預設用 **HTTP API**（便宜、低延遲）；需要 usage plan / API key / 快取 / WAF → **REST API**；雙向長連線 → **WebSocket API**

## 💸 成本

資料傳輸計費的五條規則？
?
**進入 AWS 免費**；同 AZ 私有 IP 免費；**跨 AZ 雙向計費**；跨 Region 計費；**出網際網路最貴**。
經 CloudFront 出去比 origin 直出便宜，且**回源免費**。

私有子網大量存取 S3 導致 NAT 帳單高 → 怎麼解？::建 **S3 gateway endpoint**（**免費**），流量不再經 NAT gateway 的處理費

三個標準降本手法？::**① gateway endpoint 取代 NAT ② CloudFront 降低 egress 單價與 origin 負載 ③ 每 AZ 一個 NAT 避免跨 AZ 流量**

成本最佳化的五個提問順序？
?
① 有沒有完全不需要的資源（閒置 EC2、未掛載 EBS、未關聯 EIP、舊 snapshot、未完成 multipart）
② 規格對嗎（Compute Optimizer）
③ 購買模式對嗎（SP / Spot）
④ 儲存類別對嗎（Lifecycle / Intelligent-Tiering）
⑤ 資料傳輸路徑對嗎（endpoint / CloudFront / 跨 AZ）

Budgets、Cost Explorer、CUR 各做什麼？::**Budgets = 超標告警**；**Cost Explorer = 歷史分析與預測**；**CUR = 最細帳單明細供自訂分析**

「找出閒置資源」與「找出規格過大的實例」分別用什麼？::閒置 → **Trusted Advisor**（完整檢查需 Business/Enterprise Support）；規格建議 → **Compute Optimizer**

Organizations 合併帳務帶來哪三個好處？::**用量級距折扣**、**RI / Savings Plans 跨帳號共享**、**成本分配標籤做部門歸因**

## 📈 可觀測性

CloudWatch 預設有記憶體使用率指標嗎？::**沒有**。記憶體與磁碟可用空間**必須安裝 CloudWatch Agent** 才收得到

「從應用日誌偵測特定錯誤並告警」怎麼做？::**metric filter 萃取指標 → alarm**（不能直接對 log 設 alarm）

EC2 預設監控的間隔？啟用 detailed monitoring 後呢？::預設 **5 分鐘**；detailed monitoring 為 **1 分鐘**（付費）

CloudWatch Logs 的保留期預設是多久？::**永久**——應主動設定保留期以控制成本

「把日誌即時串到 Lambda / Firehose」用什麼？::CloudWatch Logs 的 **subscription filter**

微服務之間哪一段慢 → 用什麼？::**X-Ray**（分散式追蹤）

## 🌉 遷移與混合

DataSync 與 Storage Gateway 一句話分辨？::**DataSync = 搬家**（搬完本地就不用了）；**Storage Gateway = 延伸**（本地持續以傳統介面存取雲端）

Storage Gateway 的四種型態？::**S3 File Gateway**（NFS/SMB→S3）、**FSx File Gateway**（SMB→FSx）、**Volume Gateway**（iSCSI）、**Tape Gateway**（VTL）

Volume Gateway 的 Cached 與 Stored 怎麼選？::要**減少本地儲存空間** → **Cached**（主資料在雲）；本地需要**低延遲存取全部資料** → **Stored**（主資料在本地）

什麼時候選 Snow Family？什麼時候不要？::**頻寬不足、用網路傳要數週/數月**才選；**先算一下——10 TB 在 1 Gbps 下不到兩天，此時 DataSync 更快也更省事**

DMS 與 SCT 的分工？::**DMS 搬資料**（支援 CDC 最小化停機）；**SCT 轉換異質資料庫的 schema 與程式碼**

Transfer Family 的正解情境？::**外部夥伴必須繼續用既有 SFTP/FTPS 客戶端**，後端存 S3 或 EFS

遷移策略 7R？::Rehost、Replatform、Repurchase、Refactor、Retire、Retain、Relocate
