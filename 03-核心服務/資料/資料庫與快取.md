# 資料庫與快取

`App private subnet → DB security group → RDS/Aurora`；依讀寫、交易模型、HA 與全球分布選型，而非單看「NoSQL 比 SQL 快」。

| 需求 | 候選 | 注意 |
|---|---|---|
| SQL、關聯與交易 | RDS / Aurora | engine、成本、兼容性 |
| 一般 RDS DB instance 的 AZ 故障自動切換 | Multi-AZ DB instance | standby 用於 HA，不供直接讀取 |
| 一般 DB instance 分攤讀取 | Read Replica | 複寫通常非同步，可能有 lag；不是同義於 HA 自動切換 |
| 讀取擴展兼 HA | Aurora replicas，或 RDS Multi-AZ DB cluster | Multi-AZ **DB cluster** 有可讀 reader，勿套用上述 instance 版敘述 |
| 大量 key-value、依 access pattern 查詢 | DynamoDB | partition key 與 GSI 設計、capacity mode |
| 熱資料快取 | ElastiCache / DynamoDB 專用 DAX | 快取失效、最終一致性/失效策略 |

Aurora 使用分離的叢集儲存和 DB instances；Aurora Global Database 處理跨 Region 讀取/災難情境，跨 Region 複寫仍應評估 lag 與故障切換流程。DynamoDB Global Tables 可做多 Region 複寫；強一致、交易與衝突語義要依題目限制。

**一個常見混淆**：「Multi-AZ 不能讀 standby」只對標準 RDS Multi-AZ DB *instance* 的 standby 說法成立；Multi-AZ DB *cluster* 有 reader DB instances。考試題幹的部署名詞要逐字辨識。

Spring Boot 案例：訂單狀態更新須 ACID → RDS/Aurora；查詢量飆升 → 讀 replica 或 cache，但也檢查讀寫一致性；工作解耦 → [[事件驅動與無伺服器]]。持久 DB 不靠 ASG 內的 EC2 本地檔案，見 [[EC2與負載平衡及擴展]]。

# 🧠 技術層
*它實際上怎麼運作——心智模型、機制、限制。**第一輪只讀這一層**，先把架構直覺建立起來。*

## Multi-AZ vs Read Replica 的完整對照

原筆記已正確區分，這裡補上考題實際會問的維度。

| | **Multi-AZ DB instance** | **Read Replica** | **Multi-AZ DB cluster** |
|---|---|---|---|
| 目的 | **HA / 故障切換** | **讀取擴展** | 兩者兼具 |
| 複寫方式 | **同步** | **非同步**（有 lag） | 半同步（2 個可讀 standby） |
| standby 可讀 | ❌ | ✅ | ✅ |
| 自動故障切換 | ✅ | ❌（需手動提升） | ✅（更快） |
| 跨 Region | ❌（同 Region 跨 AZ） | ✅ **可跨 Region** | ❌ |
| 計費 | standby 也計費 | 每個 replica 計費 | 3 個 instance |

> [!danger] 這組對照是 SAA 最高頻的資料庫考點
> `high availability` / `automatic failover` / `minimize downtime during AZ failure` → **Multi-AZ**
> `offload read traffic` / `reporting queries are slowing down the primary` → **Read Replica**
> `disaster recovery in another Region` → **跨 Region Read Replica** 或 **Aurora Global Database**
> **Multi-AZ 不是 DR 方案**（同 Region），**Read Replica 不是 HA 方案**（不自動切換）。題目把兩者對調就是錯的選項。

## RDS 的其他機制

| 功能 | 重點 |
|---|---|
| **自動備份** | 保留 **0–35 天**，支援 **point-in-time recovery（PITR）**。設為 0 = 關閉 |
| **手動 snapshot** | **不會**隨 DB 刪除而消失，可保留到你手動刪除 |
| **RDS Proxy** | **連線池**。解決 Lambda 等無伺服器大量短連線耗盡 DB 連線的問題；並可縮短故障切換時間、整合 Secrets Manager/IAM 驗證 |
| **IAM database authentication** | 用 IAM 憑證連 DB，免存密碼 |
| **Enhanced Monitoring / Performance Insights** | OS 層指標 / SQL 層效能分析 |
| **加密** | 建立時啟用；**既有未加密 DB 要加密 → snapshot → 複製 snapshot 時加密 → 還原**（不能就地開啟） |
| **Storage Auto Scaling** | 儲存空間自動擴充 |

> [!important] RDS Proxy 的題型
> 題幹出現「**Lambda 函式併發量大，資料庫出現 `too many connections` 錯誤**」→ **RDS Proxy**。
> 這是近年常見題，選「加大 DB instance」是錯的（問題在連線數不在運算量）。

## Aurora 深入

- **儲存架構**：運算與儲存分離，資料在 **3 個 AZ 各 2 份、共 6 份副本**；儲存自動擴展（10 GB 起，至 128 TB），自我修復。
- **Endpoint 三種**：**Cluster endpoint**（寫入，指向 writer）、**Reader endpoint**（自動負載平衡到所有 reader）、**Custom endpoint**（指定子集，例如把分析查詢導到特定規格的 reader）。
- **Aurora Replica**：最多 15 個，**故障切換時自動提升**（可設優先順序 tier），複寫延遲通常在毫秒級。
- **Aurora Serverless v2**：按需自動調整容量（ACU），適合 `unpredictable`、`intermittent`、`infrequent` 工作負載。
- **Aurora Global Database**：一個主 Region + 最多 5 個次要 Region，**典型複寫延遲 < 1 秒**，**RPO 約 1 秒、RTO 約 1 分鐘**（跨 Region 提升）。題幹要求跨 Region DR 且 RPO/RTO 極短 → 這個。
- **Backtrack**（僅 Aurora MySQL）：把叢集「倒帶」到過去某時間點，不需還原備份。
- **Aurora 與 RDS 的取捨**：Aurora 效能與可用性較佳但成本較高；題目若強調 `lowest cost` 且無特殊 HA 要求，RDS 可能才是答案。

## DynamoDB 深入

| 概念 | 重點 |
|---|---|
| **Capacity mode** | **On-demand**：不可預測流量、不想規劃容量；**Provisioned**：可預測流量、成本較低，可搭配 Auto Scaling |
| **Partition key 設計** | 選**高基數**屬性避免 hot partition。題目說「某些查詢很慢/被限流」→ 檢查 partition key 分布 |
| **LSI**（Local Secondary Index） | 同 partition key、不同 sort key。**只能在建表時建立**，共用分割區 |
| **GSI**（Global Secondary Index） | 不同 partition key。**可隨時建立**，有自己的容量。**GSI 只支援最終一致性讀取** |
| **一致性** | 預設**最終一致性讀**（較便宜）；可要求**強一致性讀**（成本加倍，且 GSI 不支援） |
| **DynamoDB Streams** | 資料變更事件流，觸發 Lambda。`react to item changes`、實作 CDC |
| **TTL** | 自動刪除過期項目，**免費**。題幹關鍵字 `automatically expire session data` |
| **PITR** | 過去 35 天內任一秒還原 |
| **Global Tables** | 多 Region **多寫入（active-active）**，**最後寫入者勝**的衝突解決 |
| **DAX** | DynamoDB 專用的**微秒級**快取，**應用程式碼幾乎不用改** |

> [!tip] DAX vs ElastiCache
> `DynamoDB reads are too slow, need microsecond latency, minimal code change` → **DAX**。
> 需要快取 **RDS 查詢結果**、或需要通用資料結構（排行榜、pub/sub、session store）→ **ElastiCache**。
> **DAX 只服務 DynamoDB**，不要拿來當通用快取。

## ElastiCache：Redis/Valkey vs Memcached

| | **Redis / Valkey** | **Memcached** |
|---|---|---|
| 資料結構 | 豐富（list、set、sorted set、hash） | 純 key-value 字串 |
| 持久化 | ✅ 支援快照/AOF | ❌ 純記憶體 |
| 複寫與 HA | ✅ **Multi-AZ 自動故障切換** | ❌ |
| 備份還原 | ✅ | ❌ |
| 多執行緒 | 單執行緒為主 | ✅ **多執行緒** |
| 典型用途 | session store、排行榜、pub/sub、需要持久性與 HA | 單純的水平分片快取 |

> [!important] 一句話
> 題目只要出現 **`high availability`、`persistence`、`failover`、`backup`** 其中之一 → **Redis/Valkey**。
> 只有「單純快取、要多執行緒、可水平擴展、資料遺失可接受」才選 **Memcached**（考試中較少是正解）。

## 專用資料庫

| 服務 | 資料模型 | 題幹關鍵字 |
|---|---|---|
| **DocumentDB** | 文件（MongoDB 相容） | `MongoDB workload` |
| **Neptune** | **圖** | `graph`、`relationships`、`social network`、`fraud detection`、`recommendation engine` |
| **Keyspaces** | 寬欄（Cassandra 相容） | `Cassandra` |
| **Timestream** | 時序 | `time-series`、`IoT sensor metrics` |
| **QLDB** | 帳本（不可變） | `immutable ledger`、`cryptographically verifiable history` |
| **Redshift** | 資料倉儲 OLAP | 見 [[資料分析與串流]] |

> [!warning] OLTP vs OLAP 的分界
> 「交易、單筆讀寫、低延遲」→ **RDS / Aurora / DynamoDB**。
> 「複雜聚合、跨大量歷史資料的分析報表」→ **Redshift**（或 S3 + Athena）。
> 題目說「報表查詢拖垮了生產資料庫」時，答案可能是 **Read Replica**（輕量）或**把分析搬到 Redshift**（重量），要看題幹的規模描述。

# 🎯 考試層
*考試會怎麼問——關鍵字反射、誘答陷阱、閉卷檢核。**第二輪與考前讀這一層**。*

## 🎯 考點速記

看到 `automatic failover` / `AZ failure` → **Multi-AZ**
看到 `offload read traffic` / `reporting slowing down primary` → **Read Replica**
看到 `region failure` → **跨 Region replica** 或 **Aurora Global Database**
看到 `too many connections` from Lambda → **RDS Proxy**
看到 `microsecond` + DynamoDB + 少改程式 → **DAX**
看到 `HA` / `persistence` / `failover` + 快取 → **Redis/Valkey**（不是 Memcached）
看到 `intermittent` / `idle most of the time` + 關聯式 → **Aurora Serverless v2**
看到 `multi-region writes` + NoSQL → **DynamoDB Global Tables**
看到「容量有剩卻限流」→ **熱分割區**，改 partition key

## 💣 真實場景陷阱

- **Read Replica 的 lag 造成讀到舊資料**：寫入後立刻讀 replica 可能讀不到。需要 read-after-write 一致性時必須讀主庫。
- **Multi-AZ 故障切換會斷線**：切換期間既有連線會中斷，應用必須有重試與連線池重建邏輯（這也是 RDS Proxy 的價值之一）。
- **DynamoDB 的 GSI 有自己的容量**：GSI 被限流會反過來影響主表的寫入。
- **ElastiCache 的快取失效策略沒設計**：lazy loading 會有 cache miss 風暴，write-through 會快取用不到的資料。TTL 是必要的。
- **Aurora 的 reader endpoint 是 DNS 輪詢**，連線池會黏在同一個 reader 上，負載不一定平均。

## ✍️ 自我檢核

1. Multi-AZ DB instance、Read Replica、Multi-AZ DB cluster，三者的複寫方式、standby 可讀性、自動切換各是什麼？
2. 「Lambda 併發量大導致 DB 連線耗盡」為什麼不能用「加大 instance」解決？
3. DynamoDB 整體容量有剩卻被限流，原因與正確解法？
4. 什麼關鍵字出現就一定選 Redis 而不是 Memcached？
5. Aurora Global Database 的 RPO/RTO 量級？它和「跨 Region read replica」差在哪？

<details>
<summary>參考答案</summary>

1. **Multi-AZ DB instance**：同步複寫、standby **不可讀**、**自動切換**。**Read Replica**：非同步（有 lag）、**可讀**、**不自動切換**、可跨 Region。**Multi-AZ DB cluster**：半同步、**有可讀 reader**、自動切換更快。
2. 問題在**連線數**不在運算量。加大 instance 只是提高連線上限，治標且昂貴。**RDS Proxy 的連線池**把大量短生命週期連線收斂成少量持久連線，才是根本解。
3. **熱分割區（hot partition）**——流量集中在少數 partition key，單一分割區容量先被打滿。解法是**重新設計 partition key 提高基數**（或加隨機/計算後綴），加容量無效。
4. **`high availability`、`automatic failover`、`persistence`、`backup`、`replication`** 任一個。Memcached 全都不支援。
5. **RPO ≈ 1 秒、RTO ≈ 1 分鐘**。跨 Region read replica 的複寫延遲較高且**提升需要人工或腳本**，RTO 無法保證在分鐘級。

</details>
